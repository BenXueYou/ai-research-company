# T20 U-Mail 企业资源与域名渠道设置

日期：2026-10-27。对应 GitHub Issue #21。状态：本地 UI、NestJS API、PostgreSQL 持久化及受控适配器业务验证完成；真实 U-Mail 资源隔离、DNS、发送和回复实收未执行，留给 T32。

## 已实现

- 平台从终端企业列表选择目标企业，配置唯一 U-Mail 供应商资源标识。供应商资源标识跨企业唯一；平台配置权限不扩大为企业渠道写权限。
- 企业管理员在平台已分配资源后维护本企业最多一套域名渠道，包括发信域名、域名发信地址、真实回复地址与默认渠道选择。业务员只读本企业状态。
- U-Mail 与 T19 SMTP 复用 `team_sending_channels`，分别受 `organization_id + kind` 唯一约束，并共享每企业最多一个默认渠道的数据库约束。将任一渠道设为默认时只取消另一渠道默认标记，不改写另一渠道地址、凭据或验证字段。
- 平台配置和企业配置均使用请求 UUID 幂等。同请求同载荷直接返回已保存结果且不重复调用适配器；同请求不同载荷拒绝。
- 默认适配器不联网，明确返回 `not_live_verified`。测试注入受控适配器验证可用、待验证、不可用、归属不一致和适配器异常边界；保存成功不冒充正式资源隔离或真实 DNS 验证。
- `billing_responsibility=platform_phase_one` 固定在服务端和数据库约束中；终端用户页面明确第一阶段费用由平台承担。本票不产生查询点数、邮件费用或账务流水。

## 参数来源核对

| 参数 | 来源与验证 |
|---|---|
| organizationId | 平台 UI 选择的终端企业 ID → POST → 受控适配器 → `umail_resources.organization_id`；测试中与平台组织ID、管理员账号ID均不同。企业管理员请求不接受该字段。 |
| resourceId | 平台独立输入 → 受控适配器；仅保存为供应商资源引用，不从企业ID或账号ID推导。甲乙企业使用不同值，并验证重复资源拒绝。 |
| domain | 企业管理员独立输入 → POST → 受控适配器 → `umail_domain`；不从登录邮箱或回复地址推断。 |
| senderAddress | 独立域名发信地址输入 → 适配器 → `umail_sender_address`；服务端仅验证其域名与明确提交的 domain 一致，不使用回复地址兜底。 |
| replyAddress | 独立真实回复地址输入 → `reply_to` → 管理员/业务员页面；测试值与登录邮箱、发信地址均不同。 |
| defaultChannel | 管理员显式勾选布尔值 → 共用 `default_flag`；不因只有一套渠道自动设为默认。 |
| 状态 | 仅取受控适配器返回；客户端不能提交资源、域名、账号或综合状态。 |

## 已验证

- `npm run typecheck` 与 `npm run build` 通过。
- T20 HTTP/PostgreSQL 测试 6 项通过：平台资源配置与费用责任、幂等、字段来源、最多一套、跨渠道默认切换、业务员只读、平台无企业写权、未分配资源拒绝、跨企业资源唯一与数据隔离、无效字段在适配器前拒绝。
- T20 Playwright 真实浏览器流程通过：平台配置资源、企业管理员配置域名渠道、请求字段白名单、回复地址展示、业务员只读及 390px 无横向溢出。
- T19 SMTP 回归 6 项通过；SMTP 账号、回复地址、加密凭据、企业隔离和权限行为保持不变。
- 所有票据测试均使用精确命名的独立 `*_test` 数据库，结束后删除；没有清空共享测试库。

- 未验证真实 SPF/MX/DKIM、域名生效、发信账号状态、回复实收、小批量任务路径、变量/内容优先级、`relpy_to`、频控、逐收件人回执或附件兼容。
