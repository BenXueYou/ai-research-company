# T19 国内 SMTP 团队渠道设置与回复地址

日期：2026-10-27。对应 GitHub Issue #20。状态：本地 UI、NestJS API、PostgreSQL 持久化及受控适配器业务验证完成；未推送、修改线上工单或关单。真实连接、DNS、发送、退信与回复实收未执行，按范围留给 T31。

## 范围与权限

- 实施依据为本地 Spec v1.2 US50～51、R31/R64、AT-14，PRD v3.2 R31，技术设计 v3.3 `team_sending_channel` 与邮件接入章节、`06-邮件接入方案复核.md`及本地 T19 票计划；未用滞后的线上票覆盖本地规则。
- 每个终端企业最多一套国内 SMTP，字段为服务地址、端口、TLS/STARTTLS、SMTP账号、授权凭据、团队回复邮箱及默认渠道标记。没有增加第二套配置、自动轮换、失败跨渠道重发、收信同步或发信入口。
- 终端企业管理员可配置；同企业业务员只能读取不含凭据的状态。平台查看权、分销关系和其他企业身份均不扩大为维护权。服务端从当前认证账号取得`organization_id`，请求不接受组织、操作者、可用性或验证时间等目标字段。

## 实现与安全

- `GET /api/sending-channels/smtp`返回本企业 SMTP 配置、默认标记及验证结果；`POST /api/sending-channels/smtp`只接受`host,port,security,username,credential,replyTo,defaultChannel,requestId`。未知字段、无效端口、明文非加密模式、无效回复邮箱及非布尔默认值均在适配器调用前拒绝。
- PostgreSQL 对`organization_id + kind`设置唯一约束，物理上限制每企业每渠道最多一套；重复配置执行原记录更新。操作者与请求 UUID 建立幂等记录，同请求同载荷不再次调用适配器或新增记录，同请求不同载荷返回冲突。
- SMTP授权凭据使用独立`SMTP_CREDENTIAL_KEY`做AES-256-GCM加密，关联数据为实际企业ID与`SMTP`渠道。数据库仅保存密文，GET/POST响应、审计和浏览器页面不回显凭据；数据库密钥指纹阻止直接换钥导致旧密文不可读。部署脚本及配置样例已加入独立密钥要求。
- 配置通过`DomesticSmtpAdapter`边界验证。测试注入受控适配器并验证`available/unavailable`；默认运行适配器不访问网络，只返回`not_live_verified`及明确的正式联调提示。适配器异常保存为不可用结果，不伪装为已验证可用。
- 管理员页面保存后清空凭据输入；业务员页面只呈现只读配置和验证结果。真实回复仍由团队在原邮箱查看，未实现IMAP/POP3或自动把客户状态改为已回复。

## 参数来源证据

| 参数 | 取值链路与核对 |
|---|---|
| host/port/security | 浏览器表单原值→POST快照→受控适配器；端口仅转换为数值，不从账号或回复地址推断 |
| username | 独立SMTP账号表单→适配器→本企业渠道记录；不作为系统登录邮箱，不从当前用户邮箱兜底 |
| credential | 独立凭据表单→受控适配器→AES-GCM密文；测试解密只用于核对原值，响应、页面、审计均无明文 |
| replyTo | `browser-reply@example.net`等独立表单值→POST→适配器→`reply_to`→只读页面；与管理员登录邮箱、SMTP账号使用不同值 |
| organizationId | 当前会话账号→服务端`accounts.organization_id`→渠道`organization_id`；浏览器请求无组织字段，测试令组织ID、管理员账号ID、业务员账号ID互不相同并逐项比对 |
| updatedBy | 当前会话账号ID→渠道及审计操作者；不以组织ID替代账号ID |
| defaultChannel | 管理员显式勾选值→POST布尔值→`default_flag`；未从“仅有一套”推断为默认 |
| verificationState | 只取受控适配器结果；客户端不能提交或覆盖，不把保存成功当真实SMTP可用 |

不同企业甲/乙分别使用不同组织、账号、SMTP账号、凭据和回复邮箱验证隔离；业务员越权提交及平台读写均为403。T19不产生查询点数、邮件额度或账务流水，因此无账务金额可核对。
