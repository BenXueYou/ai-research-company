# T15 主动更新企业及联系人并保留历史

日期：2026-10-27。范围：Spec US-38～39，PRD R05、R35～36，AT-12。未提交、推送、部署或修改线上工单。

## 实现

- 档案展示企业详情最近获取时间；联系人区展示最近成功页获取时间。用户明确点击“主动更新”后才取得新报价，再次确认费用才执行原有冻结、上游调用及结算流程。原有首次详情/联系人报价接口与本地免费查看保持原路径。没有后台 TTL 付费刷新。
- 详情主动更新锁定本企业档案对应的已核实候选名称和国家。成功后更新档案数据及获取时间；旧详情查询及结果保留。零结果、最终失败或未知状态不替换旧档案；未知状态沿用冻结和人工核对。
- 联系人主动更新锁定本企业档案名称、职位标签、页码、页大小。对同一页旧联系人标记“本次更新未返回”，再次返回则清除标记；不删除联系人或推断离职、邮箱失效。每次成功页的原始联系人响应另存只增快照，现有联系人 UUID、邮件准入、归属确认与沟通引用保持有效。首次查询与人工对账结算也写入快照；迁移补录现有联系人当前快照。
- 服务端的独立更新报价入口拒绝无效或其他档案标识；同一查询范围有在途报价时不新建冲突查询。所有实际执行仍要求报价查询 ID、终端身份、余额及原系数条件。

## 已执行业务验收

- 独立 `acquisition_t15_test` PostgreSQL、端口 3145、独立 `.scratch/t15-dist` 与 `.scratch/t15-web`：真实 Nest HTTP、会话/CSRF、数据库事务和 Chromium 从登录到档案更新流程通过。浏览器确认取消企业和联系人更新均无上游调用；再次确认才各增加一次调用。
- 来源比对：列表 `source_id=list-id-404`，详情 `data.id=detail-data-id-909`，内部候选/档案/查询为不同 UUID，联系人 `mailsouId=mail-source-old/kept`，响应中的 `id`、`fileId` 取不同值。详情上游请求仍为已核实候选名称 `Chosen Company` 与 `TUR`；联系人上游请求仍为档案名称 `Chosen Company`、选中职位 `TECHNOLGY`、第 1 页、20 条。无 `id`/`fileId` 兜底。错误来源标识被拒绝且无上游调用。
- HTTP 阶段四次有结果的查询各扣 0.2500，余额 5.0000→4.0000，冻结归零；随后浏览器又主动更新详情与联系人各一次。重复执行不再次调用。详情旧版本仍在旧查询结果中；联系人更新未返回的 `mail-source-old` 保持原 UUID 与邮箱并标记，新返回的 `mail-source-kept` 更新当前值且两个版本源快照均可查。页面显示最近获取时间及“本次更新未返回”的限定说明。
- 更新返回真实零结果时，企业档案与两个旧联系人仍保留，查询不扣点；随后受控联系人超时进入结果确认中，保留 0.5000 冻结且重复执行不再调用。
- 既有 T11 详情 HTTP/PostgreSQL 测试 1 项通过；T14 联系人 DTO 与 HTTP/PostgreSQL 测试 2 项通过。`npm run typecheck`、独立 Vite 构建与 `git diff --check` 通过。
