## Problem Statement

外贸团队需要从产品词或已知公司名找到目标采购企业，确认企业身份后获取联系人、发送单轮开发邮件并保留跟进资料。当前仓库主要包含设计文档和HTML交互原型，缺少可用于真实业务的账号、权限、事务账务及供应商接入实现。开户原型只创建组织信息，没有交付可登录的首位管理员账号；成员密码仍由创建人手填，用户缺少统一的本人修改密码入口。

平台还需要通过最多两级分销提供查询点数。不同企业之间的业务数据必须隔离，收费必须经用户逐页确认且不超过上限，线下收款和内部点数划拨必须能对账，不能因为超时、重试、跨日或重复操作产生重复扣点、重复划拨或重复发信。

本规格将第一阶段需求转换为可实施、可验收的整体契约，覆盖PRD R01～R77；后续阶段能力及未决参数不自动进入交付范围。

## Solution

正式应用后端统一采用 **NestJS + TypeScript**，前端统一采用 **Vue 3 + TypeScript + Vite + Element Plus**：Vue 3使用 Composition API 与 `script setup`，TypeScript约束组件及接口类型，Vite负责开发与构建，Element Plus提供基础界面组件。具体职责及开发约束见[技术设计第一章](./03-技术设计文档.md#一阶段架构与职责)。单HTML原型仅作为交互参考；实现须遵守已确认的业务字段来源、接口契约、校验与提交条件，并执行本规格的取值来源数据集与业务验收。本次规格修订不包含应用依赖安装或页面开发。

本方案为全新系统建设，不存在需要承接的旧前端代码、旧后端数据表或历史业务数据。前后端与数据库表结构按本规格新建，不设置旧系统迁移、旧表升级、历史数据导入或历史接口兼容要求；原型及本地试验实现不构成兼容基线。

提供四类角色的完整业务闭环：平台运营、分销管理员、终端企业管理员和业务员。

- 直属上级开户时必填电话号码和管理员邮箱，由系统生成随机临时密码，成功后一键复制账号信息并线下交付；首次登录强制改密。企业成员采用相同凭据交付方式；所有角色均可修改本人密码。
- 终端企业沿“找企业 → 核实身份 → 企业建档 → 档案内获取联系人 → 预览并确认单轮邮件 → 手动跟进”操作；所有计费查询分别确认，团队共享本企业档案。
- 分销方沿“直属下级开户与定价 → 点数订单 → 确认足额线下收款 → 库存不足则登记待补库存 → 整单预留 → 完整划拨”操作，销售与退款留痕；平台配置上游单价、点数换算系数和最低加价率，并处理异常对账。
- 终端保持找企业、企业档案库、邮件发送记录、团队发信设置、成员管理、点数用量六个入口，其中团队发信设置和成员管理仅终端管理员可维护；分销保持下级管理、点数订单、交易与利润三个入口。本人改密放右上角“账号设置 → 修改密码”。

1. As a 直属上级, I want to 开户时填写组织信息、电话号码和管理员邮箱, so that 下级组织有明确联系信息及首位管理员。

6. As a 首次登录用户, I want to 先完成强制改密才能进入业务, so that 后续使用自己的密码。
7. As a 登录用户, I want to 在账号设置校验当前密码并两次填写新密码, so that 可以主动修改密码。

## Implementation Decisions

### 模块与持久化

- 以模块化业务服务承载账号组织、查询授权结算、点数订单库存、企业档案联系人、单轮邮件与平台配置对账；通过BFF统一鉴权和租户边界。采用设计中的PostgreSQL、Redis和私有对象存储；前端技术栈按Solution确定，后端采用NestJS + TypeScript，不将原型内存状态当后端实现。
- 组织、用户账号、开户联系信息、凭据审计分别记录。组织和首位管理员原子创建；账号邮箱全平台唯一，由数据库约束处理并发占用；开户电话必填国家区号、默认中国大陆（+86），且跨组织唯一。密码只持久化加盐摘要，成功结果当次展示明文用于交付，详情与日志不可回查密码。
- 业务实体包括内部点数账户、采购入账、点数订单、只增账务流水、查询授权与执行、候选、企业档案、补充字段、联系人、归属确认、时间线、附件、发信渠道、公共模板、邮件批次与收件人、企业日额度与额度事件。逻辑字段以技术设计为准，物理表结构与数据库初始化脚本在开发时新建。
- 数据写入使用事务和幂等边界；外部调用与本地授权通过既定Outbox思路衔接。不得用自动重试实现未知结果的“补偿”。

### 身份、权限与密码（R33、R35、R38～R43、R65、R70～R77）

身份参数以[已批准身份规则](../docs/decisions/001-t01-identity.md)为权威来源，T01～T05必须复用；密码、临时凭据有效期、登录邮箱等价及会话失效策略已经确认，详见PRD身份规则补充。电话禁止空格；平台恢复流程已移出一期。收件邮箱大小写不敏感规则独立于登录邮箱规范。

- 仅平台初始账号super_admin使用固定非邮箱登录标识，初始化与首次强制改密按身份决策执行；其他账号的登录邮箱取开户或成员创建表单；用户名就是该邮箱，不另行生成用户名，不以电话、组织标识或发信地址替代。一个账号归属一个组织；换合作关系另开户并使用不同邮箱。
- 开户、成员创建、重置成功均提供一键复制邮箱与随机临时密码；一次性展示结束后只能按权限重置。复制失败允许在当前展示中重试，不再次创建组织。
- 创建和重置均置必须改密状态；临时密码认证只允许本人强制改密及退出，服务端阻止业务访问。本人主动改密校验当前密码、两次新密码一致，成功后退出当前登录并用新密码登录。
- 企业成员重置仅本企业管理员操作，下级组织管理员重置仅直属上级操作；下级详情提供重新生成入口。旧密码在重置成功后立即无法认证，连续重置仅最新密码有效。平台账号由数据库初始化内置，一期不实现平台管理员恢复逻辑；下级与成员重置权限保持不变。
- 组织链最多平台→一级分销→二级分销→终端；平台和一级可直开终端，二级不能再开分销；成员不计分销级数，组织上级不可迁移。
- 分销可看授权范围内开户、余额、交易、汇总用量，不能从页面、日志、明细或导出获取关键词、企业名称、联系人或邮件。平台全链查看不授予跨级交易、重置或跨企业写入权限。
- 企业内共享档案但保留操作权限差异；不同终端企业的原始数据、缓存及经营资料隔离。停用不清余额历史、不自动级联；停用账号不能通过密码重置恢复启用。
- 停用组织与直属上下级之间暂停新增交易，仍正常启用的下级可使用余额及向自己的下级销售。终端停用停止尚未执行查询与邮件，在途只核对并按原规则结算；已收款未划拨订单保留销售预留且暂停，不自动退单。

### 查询、标识与结算（R01～R11、R22～R28、R32、R35～R37、R45～R46、R53～R56、R61～R62）

- 公司名免费企业列表与产品词最小进口商候选分开；产品词要求采购企业所在国家、贸易时间和产品词，不自动扩大条件。商品目的国不能推断为采购企业所在国家，映射未核实前不得将生产计费能力视为就绪。
- 候选先选择和核实，详情建档和联系人再分别确认；多个匹配或国家歧义不得默认第一条。身份未确认不继续联系人或发信；人工选择不能豁免详情国家强校验。
- 逐接口DTO保留字段、分隔符、判空、页码和原枚举；列表用`name/countryCodes`，详情用已确认`name/countryCode3`，详情按`data.id`判空，联系人用`companyName`及`mailsouId`。不将列表标识、内部主键、`fileId`相互替代，也不增加字段兜底。
- 每次仅获取一页；详情、联系人、下一页与主动更新都独立授权。接口未配单价不得执行计费查询；报价使用经验证的本页最大计费条数与接口单价，`row-count`不能当通用报价接口。
- 可用余额=余额−查询冻结−销售预留，预留和冻结已包含在余额中。用户确认后锁定条件、页码、系数、上限并先原子冻结；不足不调用。查询只动终端内部点数账户，不重复扣上级库存；内部划拨不操作上游余额。
- 成功页扣点=min(四舍五入至4位小数的“该页腾道实际扣点合计×确认时系数”,确认上限)，先汇总再取整。成功释放差额，真实零结果或最终失败释放/退回全部；不因电话、网址缺失或联系人无邮箱退款，不以空字段替代企业判空。
- 超时或保存不明进入结果确认中并保留冻结，不盲目重试；长期未决平台按依据核对。最终失败退款后迟到结果保留且不重扣；成功名单不因后续匹配失败退款；平台承担失败上游费用和超额成本，未执行后续步骤暂停重新确认。
- 本企业本地查看免费；其他企业首次取得数据仍独立查询。主动更新须再确认费用，不因TTL过期付费刷新；未返回旧联系人保留并标记，不推断离职或邮箱失效。
- 腾道数据可按指定设计前提落库并在当前分销体系内供终端查询查看，不可导出；该前提不是已核验合同。账务导出不得夹带第三方数据，用户自上传附件依独立访问规则下载。

### 内部点数、订单与成本（R01～R04、R12～R21、R40～R45、R66～R69）

- 平台共用腾道账户，各级内部记账；点数换算系数X平台统一、默认1，分销只调每点售价。内部点数余额、划拨、扣点统一4位小数；人民币金额、每点售价、换算系数均保留4位小数，需要舍入时四舍五入。最低加价率m=0.01（1%）。
- 点数订单库存充足时为未收款→确认收款并整单预留→已收款待划拨→已划拨；库存不足但款已到账时为未收款→登记足额收款并锁价→已收款待补库存→补足后整单预留→已收款待划拨→已划拨；一单一笔足额线下收款一次完整划拨，禁止分期、拆分、多单合并付款、款项复用、重复划拨。
- 确认收款仍校验直属关系、组织启用、足额款项及售价下限。库存充足时收款与整单预留原子完成；仅库存不足时登记真实收款、锁数量售价，本单不预留、不增加买方余额、不退款。补足后由直属卖方统一处理，逐单原子检查可用库存并整单预留，再完整划拨；不足的订单继续等待，不拆单、不合并付款、不因补库成本变化要求追加付款，重复操作幂等。
- 平台销售库存与分销库存均采用移动加权平均成本。售价≥剩余库存移动加权平均成本×(1+m)，m=0.01。新平均成本=(剩余库存成本+新采购成本)/(剩余点数+新增点数)；平台新增点数取销售用途采购按入账X生成的内部点数，成本取该笔人民币采购金额；历史已售成本毛利不重算。
- 补足上游额度、失败查询和超额费用单独归集为平台承担费用，不进入销售库存成本、不抬高最低售价。已记损耗与后续补充值关联核对，同一损耗只计一次费用；充值的资金支出和额度变动仍完整记录。平台报表分列销售毛利、平台承担费用和扣除该费用后的结果，后者不称净利润。
- 未收款订单按最新成本和m重验，低价阻止并由上级重新定价，不自动涨价；已收款按原数量售价履约，卖方承担后续成本差额，不超库存。
- 划拨在同一事务将卖方预留点数转到买方，卖方减买方加；缺库存收款登记分支按补库履约，不退款；其他符合R44的已收款未划拨订单才可整单退款，由卖方确认线下退款完成后关单释放预留。已划拨不通过普通划拨冲销退款。
- 销售用途采购按入账X生成内部库存，之后X改变不重算旧余额；补足上游额度、承担失败或超额费用的充值不增发内部库存，并按用途留账。
- 降低X前核算全链未消耗点数覆盖，含销售预留和查询冻结但只计一次；旧授权按旧X，其他余额按拟新X，并区分上游已扣本地未结算在途项。覆盖不足先补上游才生效；系数调整提前告知。
- 终端用量仅余额、冻结、扣点及退款流水；分销独立保留交易利润。内部点数无有效期，上游到期不清零内部点数，也不对未成功查询扣点。通知仅系统内，平台继续监控上游余额、有效期和配额。

### 联系人、邮件与每日额度（R26～R31、R47～R52、R57、R60、R62～R63）

- 联系人放档案页签；保留职位筛选、邮箱可信度、单次最多200条提示。返回上限不能当企业实际联系人数。职位标签保持原枚举，包括既有拼写`TECHNOLGY`，不擅自纠正接口值。
- 归属不一致默认不选，逐条说明确认后才准入；原返回公司名保留。企业邮箱优先，个人邮箱缺省不兜底；按最终邮箱同批去重，冲突变量由用户选来源。
- 退订仅标记，默认不勾选，手选后提示确认；不升级为全局/企业强制屏蔽，也不绕过供应商黑名单、退订或拒投限制。退订标记仅作用于该条联系人，不传播至相同邮箱的其他联系人；收件邮箱大小写不同视为同一邮箱，同批去重时仍由用户选择冲突变量来源。未批准的加号别名/圆点合并不启用。
- 从档案联系人发起写信：公共模板→修改本次内容→补全变量→预览→选择本批渠道→确认退订提示与额度→单轮发送。保存、预览和发送不回写公共模板；内容变化后须保证预览与最终快照一致。只允许模板预设附件。
- 每企业国内SMTP和U-Mail域名渠道各最多一套，可设置默认，每批固定选一种，不自动轮换或跨渠道重发。平台统一采购并隔离U-Mail资源，第一阶段承担费用，企业配合域名验证；两渠道都有可收信回复地址，不接自动收信。
- U-Mail任务API仅作为手动确认单轮的执行方式，隔离能力、小批量路径仍需联调；供应商`relpy_to`保留原拼写，验证`tpl_id`优先于编辑内容的风险，不让公共模板覆盖本次修改。供应商SMTP接口不等于任意邮箱SMTP。
- 邮件状态区分排队、已提交发信服务、失败、结果待确认；有可靠投递证据才显示已送达，受理不等于送达、阅读或回复。超时先核对，不自动重发；仍不明确须提示可能重复并由用户决定。
- 每企业、团队与两渠道共用日额度，数量按本批最终去重地址数；确认时原子预占，受理转已用，明确未提交释放，不确定保留，重复回执幂等。邮件不扣内部查询点数。
- 额度按Asia/Shanghai零点重置、不累计。跨日未执行暂停并解除原日未执行预占，次日用户重确认占新日；已提交不明留原日核对，迟到结果只改原日，不释放后再占新日。

### 档案、时间线与附件（R33～R36、R57～R66）

- 固定补充主营产品、采购需求、合作意向、下次跟进时间，与源数据分区并留修改人时间，其他写备注；跟进日期只展示筛选，不自动提醒。保留星级和标签，客户四态由人工改动，邮件事件不自动置已回复。
- 企业档案管理员软删除恢复；人工时间线仅创建人编辑、管理员软删除；系统邮件记录不可手改删，仅由系统依据渠道更新。各类记录的权限不能相互推定。
- 统一时间线倒序并按邮件、回复摘要、备注、WhatsApp筛选。WhatsApp手工只记时间、联系人或号码、摘要、附件；下次跟进用档案字段，不增加方向、结果或我方账号独立字段。
- 档案附件仅上传、下载、管理员软删除；继承白名单jpg/png/webp、pdf/doc/docx/xls/xlsx/ppt/pptx、zip/rar，≤20MB/文件、≤50/企业。服务端扩展名与MIME校验、私有访问、号码加密脱敏、操作记录继续适用；保留安全扫描设计但需实际验证。档案附件不自动成为邮件附件，也不能变为腾道数据导出通道。

### 上游契约与运行约束

- 腾道共享账户跨接口合并200次/分钟、数据类30,000次/日，免费数据也占调用次数；业务类日配额按账号配置。配额与点数余额分开限制，实际权限与商务配置须核验。
- 业务`success/code`与HTTP状态分开；`code`按字符串处理并兼容数字，不用`msg`分支。逐接口判空、列表/对象、分页、游标、请求/响应大小写分别处理，不用“先content再list”等猜测兜底。
- 国家码、分隔符、时间跨度和页码限制保留技术契约；通用贸易边界`pageNo×pageSize≤10,000`且`pageNo≤1,000`不自动套用于所有接口。错误与零结果先区分参数错误及越界。
- API密钥、令牌、邮箱授权凭据采用密钥管理；记录traceId、脱敏参数、耗时与证据，敏感操作审计不可覆盖。保留同企业本地数据降级及最近获取时间，不因上游不可用自动付费刷新。

## Testing Decisions

### 已确认的主要验收边界

用户已确认以完整用户流程验收，覆盖真实服务端权限与账务；腾道和邮件服务在外部适配器边界使用可控响应，保留正式联调检查。主要入口为用户界面驱动的系统级流程，贯穿真实应用服务与测试数据库；为权限绕过、并发和回执乱序补充公开应用接口驱动的集成场景，不为内部函数逐一建立测试边界。

好测试验证用户能观察到的页面、认证结果、业务结果、余额、流水及外部提交参数；不依赖内部函数名或内存实现细节。拒绝路径同时验证没有外部付费调用、没有错误账务变动或越权数据泄露，不能只检查弹出提示。正式服务商联调与可控响应验收分开报告。

### 既有测试先例及限制

仓库已有基于Playwright和Edge的HTML原型交互检查，涉及导航、查询选择到提交、标识来源、结算、收件人和邮件跨日额度、档案权限及分销订单；既有验证清单记载v3.0的29组模拟检查。部分检查直接操作原型内存状态，只能作为场景先例，不作为正式应用已有测试或实现的基线。正式应用须按已确认的业务规则新建系统级流程与真实数据库集成测试，账号场景按当前开户及密码规则验收，不沿用原型中已过时的行为。

### 本轮补充验收

- 电话包含空格时前后端拒绝；默认+86、跨组织唯一及并发开户仍需验证。
- 企业默认日额度2000封，按企业修改后互不影响；两渠道与全团队共享，超限拒绝。
- 使用仅大小写不同且变量不同的邮箱验证同批仅一封、变量由用户选择；退订标记不传播至另一个同邮箱联系人。
- 模板附件验证平台管理员权限及2MB/10个/20MB边界，产品格式不设白名单但渠道拒绝仍生效；不改变档案附件原限制。
- 默认2年到期仅标记，未人工清理前不自动删除；管理员按原对象权限清理且保留记录。
- T05和US14/R77平台恢复分支已撤出一期，不作为当前验收要求；数据库初始化账号仍验证首次强制改密、重复初始化不覆盖已改密码。

### 取值来源数据集与完成标准

- 使用刻意不同的组织ID、用户ID、开户电话、登录邮箱和团队回复/发信地址，逐步比对开户表单、创建账号、复制内容及登录请求，不允许电话或发信地址替代登录邮箱。
- 使用列表标识、详情`data.id`、内部企业ID、`mailsouId`、无关`id/fileId`各不相同的数据；采购企业所在国和商品目的国也不同。对比用户选择快照和最终请求，明确name、countryCode3、companyName、mailsouId及邮箱变量来源。
- 用两个不同mailsouId共享同一最终邮箱、不同称呼变量的数据验证去重与来源选择；用已提交不明和未执行收件人混合批验证跨日。
- 余额、费率、成本和额度的测试值只作为夹具，不成为系统默认值。正式联调的付费调用和邮件投递应作为明确执行的独立验收，不在生成规格时实际执行。
- 交付报告需列出已执行场景、参数来源比对结果、账务结果及未验证流程；构建、类型检查和无关测试通过不能代替此矩阵。所有适用且参数已明确的可控场景通过后方可确认相应实现完成，正式供应商检查另列结果。

## Out of Scope

- 第二阶段的完整贸易明细与分析、社媒、送达检测、搜索历史、地球与计数器；第三阶段AI、Agent、WhatsApp主动触达等，不因已有供应商接口提前开放。
- 任意层级分销、组织迁移、自动转旧余额或业务数据、跨级交易、跨级密码重置、客户认领、部门层级和成员间客户隔离。
- OAuth/LDAP/SSO、邮件邀请、短信验证、短信/邮件找回密码、手机号登录、多组织选择登录；除平台初始账号super_admin外不新增独立用户名。
- 线上支付、提现、分期、拆分划拨、多单合并付款、已划拨点数普通退款或冲销、净利润保障。
- 独立线索池、独立关键人页、独立创建营销任务、终端模板管理、自动收信、定时/多轮自动跟进、供应商会话同步。
- 业务员临时邮件附件、把档案附件自动附到邮件、档案附件预览/重命名/替换、自定义档案字段、未确认的单附件恢复。
- 跨企业原始缓存复用、腾道数据导出、自动付费刷新、未授权整页候选建档或全量翻页、结果不明自动重试或跨渠道重发。
- 本规格产出不包含代码实现、部署、数据库实际建表、真实扣费查询或真实发信；功能清单、Excel及原型的版本同步应另行执行。

## Further Notes

### 部署与预配完成标准

T01承担F-01的基础单环境部署脚本、配置、新库初始化及初始平台账号引导交付；后续首次引入基础设施的票扩展同一部署入口，实际运行证据随对应票记录。T21承担M-04的最小平台受控公共模板预配工具、版本及附件引用验证和操作说明，不扩建终端模板管理。具体边界按技术设计第一章；模板附件配置按已确认的平台管理员及2MB/10个/20MB规则执行，正式渠道兼容性仍是相关分支验收前置条件。

### 待决参数与生产验收前置条件

以下保持开放，实施时不得根据字段名称、旧例子或竞品功能自行确定；可先完成不依赖这些值的模块，依赖项在明确前不得宣称验收通过：

1. 电话禁止空格已确认；平台账号数据库内置、恢复逻辑撤出一期，不再作为待决项。电话必填国家区号、默认中国大陆（+86）及跨组织唯一性已经确认。密码、登录邮箱及会话规则按已批准身份决策执行，不再列为未决。
2. 平台库存移动加权成本、补足额度/失败/超额费用单列及避免重复计费规则，以及库存不足时登记收款、不退款、补足后逐单完整划拨均已确认，待业务验收；不再作为未决决策。
3. 产品词国家映射与贸易方向、企业关联、数据覆盖填充率、实际接口单价、最大计费条数和最高报价算法；长期结果确认期限及部分结果/批量结算边界。
4. 腾道账号权限、配额、有效期、书面授权及数据保存期限；当前分销授权覆盖是指定设计前提，尚非已核验合同。
5. U-Mail账号及任务资源企业隔离、小批量路径、变量映射、本次内容生效、频控恢复；SMTP/U-Mail真实DNS、回复实收、回执及退信能力、默认2000封及按企业配置的实际执行、跨日联调。
6. 上游拒投及模板附件双渠道兼容仍须验证。本地退订作用域、收件邮箱大小写判重、平台管理员模板配置及2MB/10个/20MB限制、附件默认2年到期标记后手动清理均已确认；单附件恢复仍在一期范围外。
