## 1. 基线、结论与适用范围

只读代码基线：HEAD `ed77c5546c693a2d6db305608a67a626e6a8af2d`及工作区新版需求。开始时CONTEXT、02、08、09已有修改，11为未跟踪文件，均保留。应用代码未修改。旧技术设计的新库前提、单候选建档、逐页强制确认及人工结算放行业务的冲突描述由03 v3.4及本文替代；既有权限、筛选、标识、详情判空、邮件与账务规则保持。

以下为待实施物理结构设计。新增表均带organization_id；跨表引用使用`(organization_id,id)`唯一键/复合外键，不能仅用应用层查询替代企业隔离。

| 对象 | 设计字段及约束 |
| --- | --- |
| `company_profiles`扩展 | 保留id及所有人工字段、软删除字段；detail_id/detail/query_id允许NULL；country_code3可NULL但非空时沿用三位码约束。新增identity_state=`pending/verified/conflict`、detail_state=`absent/ready`、current_identity_id、row_version；无资料用NULL，不能伪造空详情或详情查询 |
| `company_profile_sources`新增 | id、organization_id、profile_id、source_kind=`company_candidate/product_candidate/legacy_detail`、source_record_id、source_payload、search条件快照、page_no、actor_id、created_at；唯一`(organization_id,source_kind,source_record_id)`。产品词的筛选国家是搜索约束，不冒充来源返回的企业国家 |
| `company_profile_identities`新增 | profile_id、经用户确认的candidate_id、source_id、name、country_code3、核实人/时间、evidence_reference、version、status；追加历史，不覆盖来源。联系人入参资格由该记录和经核实契约决定，不由detail_state决定 |

| 查询表扩展 | 详情查询增加target_profile_id、identity_version；三类查询增加batch_item_id、result_state、billing_state、dispatch_state、request_snapshot、result_reference、policy_version。详情新增路径允许candidate_id来自对应已核实身份；现有query_id、trace_id、账单引用仍分别保存 |
| 联系人与历史 | 保持mailsou_id、returned_company_name、query_company_name、归属说明、退订及source_history；查询成功发布时幂等upsert，不等待settled。更新未返回的联系人继续保留；人工内容不由供应商快照覆盖 |

同一来源重复入库由来源唯一键返回同一档案；不同来源只有已核实的同域稳定键命中才自动关联。同名及“名称+国家”仅用于展示可能重复项，不做唯一企业键。用户可选择本企业已有档案或另行建档，保存其决定与依据；有关联冲突的项目单独返回，其他项目可成功。已软删除档案不自动恢复，按原管理员恢复权限处理。

尚无稳定键证据时可以建立待核实初始档案，但不能宣称不同搜索之间已自动识别同一家。并发相同来源通过唯一约束串行归属；并发不同来源若具备可靠键则键唯一约束返回已有档案；只有同名时保持待用户决定，不自动合并。

详情补入时保留目标profileId、人工字段、时间线、附件和邮件。若返回detail_id已属本企业另一档案，标记关联冲突并展示已有档案，由用户解决关联；不新增自动合并/搬迁历史能力，不覆盖目标，不丢结果证据。若可靠身份已证明同一家，后续查询定位已有规范档案；既存冲突的人工资料合并不混入本轮。详情国家冲突不发布，保留历史有效资料。零结果不删除初始档案。

## 5. 名单选择、接口与批次授权

### 5.1 搜索快照及名单入库

新增`company_search_sessions`保存本企业搜索种类、完整原条件、版本和已获取页引用；已有名称/产品词查询行作为页面证据，不能重建成另一份供应商调用。当前页返回时前端默认选择该页全部，可剔除；选择集合按搜索会话隔离，切换条件不带入旧选择。默认选中不提交、不核实身份、不授权费用。

用户选择所有页时，服务端按该接口可证明total和分页上限生成缺失页清单；已有页直接复用。免费页无需点数确认，但仍受用户主动操作、配额、权限和分页限制；收费页生成总上限一次确认，未确认不得调用。total未知或无法证明总上限时返回能力不足，不以贸易row-count替代，不暗中请求付费页来探测页数。结果增加不扩展原授权；减少时未发送多余页取消并释放相应冻结。返回排序漂移无法保证跨页全量时记录证据限制，不宣称绝对完整。

所有页成功结果逐页进入可选集合，剔除项保持；失败/处理中页独立展示。获取与保存是两个动作；入库入口仅消费提交时已取得的候选，不在后台把之后到达的名单自动入库。

### 5.2 拟定应用接口

以下`/api`路径是本地目标契约，不是腾道接口，也不是已实现路由。严格拒绝未知字段，租户与actor取当前会话；所有写入保留现有认证、强制改密及CSRF保护。金额均为四位小数字符串，ID为本地UUID，页码/页长保留当前接口范围。

| 方法与路径 | 输入DTO | 结果及约束 |
| --- | --- | --- |
| `POST /company-profile-imports` | `{requestId,items:[{sourceKind,sourceRecordId,decision:'create'|'link',profileId?}]}` | link必有profileId，create不得有；逐项`created/linked/needs_resolution/rejected`及profileId/reasonCode。事务以单项为边界；相同requestId+相同内容回原结果，改内容409；不得出现上游调用/冻结 |
| `POST /company-profile-identities/confirm` | `{requestId,profileId,candidateId,expectedProfileVersion}` | 单条身份版本及contactsEligible/reasons；绑定到明确线索的身份候选集合，不能互斥同次名单其他企业；国家冲突拒绝 |
| `POST /company-query-batches/quote` | `{requestId,operation,selection,refresh}` | operation为list_pages/detail/contacts；selection见下文。返回batchId、confirmationVersion、manifestHash、coefficient、maximumPoints、逐项上限及复用/不可执行原因；不冻结、不付费调用 |
| `POST /company-query-batches/confirm` | `{requestId,batchId,confirmationVersion,manifestHash}` | 原子确认并冻结一次，返回批次快照；不接受前端金额/系数。未确认时价格、系数、身份版本有变化返回409重新报价；已确认批次锁旧版本 |
| `GET /company-query-batches/:batchId` | 无body | 授权范围内逐项状态、结果引用、失败原因、可重试性、冻结/实扣/释放、金额证据待定标记；读取不触发查询 |
| `POST /company-query-batches/:batchId/retry-quote` | `{requestId,itemIds}` | 只允许明确失败项，建立新批次并记录retry_of；成功、零结果及处理中项拒绝；收费重试再走confirm，免费重试由本次显式操作执行 |

selection是带operation的互斥DTO：list_pages用`{searchSessionId,mode:'all_remaining'}`；detail用`{profileIds}`；contacts用`{items:[{profileId,positionTags,pageNo,pageSize}]}`。refresh对detail/contacts为必传布尔值，list_pages必须false。联系人多页只能执行明确清单，不由“批量联系人”推导后台自动翻尽每家企业。单页既有入口保持，最终接入同一授权/结果/结算逻辑；不得保留可绕过批次冻结的第二条执行路径。

免费批次的quote返回`requiresPointConfirmation=false`并不派发；由该次用户操作显式调用confirm派发，maximumPoints为0，不冻结点数。混合复用及收费项的批次只为需要新调用的项报价；本地已有数据、成功项、处理中项不会再次入清单。主动更新在原数据可读前提下建立新查询。

状态读取及入库、身份、报价/确认/重试对终端admin/sales开放，组织须启用。平台只读审计与已有异常处理按原平台入口，不因此获得终端发信/修改权；分销无权读取候选和查询内容。确认和真正派发前再次校验组织、账号、身份及来源版本；停用后尚未发送项停止并释放，已发送项只核对，不重试。

### 5.3 批次持久化与金额

- `company_query_batches`：organization_id、actor_id、operation、request_id、request_hash、confirmation_version、manifest_hash、coefficient、price/policy版本、maximum_points、confirmed_at、dispatch_status、retry_of。`(organization_id,actor_id,request_id)`唯一。
- `company_query_batch_items`：batch_id、目标/页面引用、identity_version、request_snapshot、source_snapshot、result_state、billing_state、dispatch_state、maximum_points、实际费用、charged_points、result_reference、error_code/reason、retry_of；批次内规范请求键唯一。
- 建立跨批次活动请求唯一键（企业+操作+规范目标/条件+页码+更新意图），阻止多个requestId对同一在途目标重复调用；复用引用已有item，不重复冻结。身份/条件改变不得借此覆盖旧请求。
- 确认事务锁批次、活动请求占位及终端账户，计算可用=balance-query_frozen-sales_reserved；不足全部拒绝且无派发。冻结总额后同事务写逐项占用和待发送任务；网络调用在事务外。统一锁顺序，结算重试整个数据库事务，不重试供应商调用。
- 保留每个已核实结算页先汇总上游实际费用再`ROUND(...,4)`及封顶。批次总额度是已证明逐项额度之和，各项不能借用未获授权的其他项额度，总实扣不超过总确认额。E02/E06未满足前只实现接口与受控策略，不启用真实批量报价，不默认整批/逐条取整或平均分额度。
- 单项超额由平台承担，原授权不加扣；按既有规则暂停该批次尚未派发的收费项并释放其占用，重新确认才继续，不暂停其他批次和查看/发信。其他已经发出的项继续核对，不能撤回或重复执行。
- 原查询流水唯一(query_id,event)继续防重；新批次ledger以item和经济事件唯一关联原流水，不能在两张表各自扣一次。退款新增独立幂等事件引用原settle；已settled后最终无法提供结果按R06退款，禁止覆盖旧流水。平台损耗/补充值沿用去重与费用不重复确认规则。

## 6. 状态、发布与后台恢复

### 6.1 三种状态独立

档案identity_state如第3节。每项查询另有result_state=`not_requested/pending/ready/zero/failed`及billing_state=`not_required/quoted/frozen/awaiting_evidence/settled/released/refunded`。发送状态dispatch_state=`not_sent/sending/sent/unknown/cancelled`仅供内部恢复。批次摘要由项目计数生成，不以“整批完成”控制单项可用。

| 事件 | 结果状态 | 账务与动作 |
| --- | --- | --- |
| 未确认报价 | not_requested | quoted；无冻结、无派发 |
| 确认并准备发送 | pending | 付费frozen；免费not_required；派发前重验准入 |
| 有效非空结果已保存 | ready | 费用不明awaiting_evidence，立即发布到原档案或名单，不等账单 |
| 已有可靠费用但结果不明 | pending | 保存证据并保留冻结；不因费用先到就扣用户点数 |
| 可靠结果与可靠费用齐备 | ready | 原子settled、释放差额，后台更新流水；缺电话/邮箱不当成零结果 |
| 确证零结果 | zero | 实扣0、释放冻结；上游费用若迟到记平台费用，不重扣 |
| 超时、进程崩溃、响应结构异常、国家冲突 | pending | 冻结保留，结果及发送状态待确认；不自动当failed，不重复调用 |
| 有证据确认最终失败 | failed | 释放全部；已扣按原交易退款；上游费用单独记录 |
| 失败退款后的迟到结果 | ready（带late_after_failure标记） | 保存并通过原校验后发布，billing保持released/refunded；不得重新结算扣点 |

ready要求已通过原有业务校验并在数据库提交，供应商成功标志、原始JSON入库均不能单独代替。国家冲突保留为待核实证据，不覆盖已有ready资料；后台恢复后满足原校验才发布。零结果沿用详情data.id=null、各分页接口原判空规则，不凭页面空数组推定。

上述冻结与结算转换只适用于收费项；免费项始终为not_required，不产生查询点数流水。若真实零结果或最终失败已获可靠结果证据，可先释放用户冻结；供应商费用尚未知时继续核对平台成本，不能因成本证据未到而重新冻结或延迟放行业务。

结果发布、档案/联系人upsert及事件在一事务中幂等完成；账单处理可在另一个事务到达，两者都通过同一item行锁确认当前事实。重放有效证据不重复联系人、不重建档案、不重复扣费。旧state字段在过渡期保留财务终态含义，新调用方使用明确状态；不能把awaiting_evidence伪装settled来兼容旧页面。

### 6.2 后台任务与证据接口

`company_query_jobs`保存item_id、job_kind、next_attempt_at、lease_owner/lease_until、attempt、last_error及checkpoint。任务种类为dispatch、recover_result、collect_billing、settle。通过短事务`FOR UPDATE SKIP LOCKED`领取并提交，网络期间不持行锁；租约参数由运行配置显式提供，不设业务失败期限默认值。worker在启动装配中注册、支持优雅退出，周期及并发受共享账号实际限额约束。

dispatch领取后在数据库写sending再调用。若崩溃发生在写sending后、确认外部响应前，无论实际上是否发出，一律进入unknown并先核实；租约失效不重发。能证明not_sent的项才可恢复发送；供应商若提供幂等/请求状态能力，须E03/E05证明后接入，不能假定恰好一次。收账/收结果失败可以恢复只读核对，不能借恢复调用新业务查询。无证据的请求保持未知并告警，不以次数或固定时长判最终失败。

新增内部Interface（目标契约）：

```ts
type EvidenceLookup = {
  itemId: string; providerRequestReference: string | null;
  traceId: string | null; endpoint: string; sentAt: string;
  requestHash: string;
};
interface QueryEvidenceAdapter {
  lookupResult(input: EvidenceLookup): Promise<unknown>;
  lookupCharges(input: EvidenceLookup, cursor?: string): Promise<unknown>;
}
```

unknown是供应商原始响应的隔离点：逐接口解析器验证并输出本地`pending/confirmed/unavailable/conflict`及证据引用；不得把未校验对象传给结算模块。正式HTTP Adapter和受控测试Adapter满足同一Interface；现有业务Adapter继续负责一次查询，证据Adapter不能在lookupResult里重新调用收费查询。没有只读恢复能力时返回unavailable并暴露阻塞，不伪造成功。

`company_query_evidence`追加保存供应商账号引用、endpoint、provider_request_reference、trace_id、billing_reference、供应商证据ID/版本、hash、金额/单位、发生与接收时间、关联状态。去重键依E03核实后的稳定账单标识；同ID不同金额保留冲突，不能简单ON CONFLICT忽略或再次扣费。无账单唯一标识不得拿请求hash充当证明。

逐请求费用可能有多条记录：只有核实完整性、水位或终态后才汇总为最终费用；游标/checkpoint与已接收证据同事务推进，重复分页安全；不以当前读到一条账单认定费用已全到。共享账号余额差不能归因单项请求。平台恢复录入也须走证据校验、相同结算入口和审计，不提供无依据扣款或先审核才使用结果的流程。
