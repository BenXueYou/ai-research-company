## 一、产品定位

### 1.1 一句话定义

面向外贸获客场景的**多级分销 SaaS 平台**：以腾道全球贸易数据为底座，平台按点计费，点数池经多级分销二次分销到终端企业；终端用户的核心链路是「**搜索企业 → 落库建档 → 挖出关键决策人 → 邮件触达 → 企业数据维护沉淀**」。

### 1.2 目标用户

| 角色 | 特征 | 核心诉求 |
|---|---|---|
| **平台运营方**（我方） | 持有腾道点数池，建设分销网络 | 点数进销存与毛利可控可查；分销商开户与管理；平台成本对账 |
| **分销商**（一级/二级） | 批量采购点数再向下分销，赚取差价 | 对下级开户、划拨点数、自主定价且**利润点有机制保障**；看不到下级客户资料（数据安全即招商卖点） |
| **终端企业 · 业务员**（主要用户） | 每天开发新客户，英语沟通，不熟悉数据分析 | 快速找到能联系上的人，知道该联系谁、说什么 |
| **终端企业 · 管理员** | 管小团队，背业绩指标 | 成员管理、点数用量可见、企业数据资产沉淀 |

### 1.3 产品边界

**做**：

- 用户管理与多级分销体系（开户、角色、双层数据权限）
- 分销计费与成本中心（点数池、划拨、牌价、利润核算）
- 第三方企业数据对接与落库
- 企业档案库与数据维护（聊天记录、附件、备注、补充内容）
- 邮件发送与营销

**明确不做**：

- 商机管理、订单/合同/PI、回款售后、独立站建站、团队沟通质检、移动审批（属成交后管理，是小满 OKKI 的存量优势区，我方资源聚焦获客前半段）
- **线上支付与提现**：分销结算走线下 + 系统对账单；接支付通道涉及分账合规，如需另行立项
- **第三方数据任何形式的导出下载**（见 §4.2）
- 终端企业内部部门级组织与成员间数据隔离（小团队全员可见；如需个人级隔离另行提需求）

### 1.4 差异化主张

| 差异点 | 说明 |
|---|---|
| **数据字段更深** | 直连腾道，可暴露发票币种、贸易术语（CIF/FOB/CFR/EXW）、集装箱号、提单号、船名等专有字段（随第二阶段贸易模块释放） |
| **分销计费透明** | 点数进销存、牌价、毛利全链路可查；**查询前先预估点数**，不烧冤枉点数；分销商利润点由定价下限强制校验从机制上保证 |
| **企业数据维护** | 沟通记录（含 WhatsApp 手动登记）+ 聊天截图附件 + 备注 + 补充内容统一沉淀在企业档案时间线，不依赖任何平台授权，补齐竞品 WhatsApp 留档断档 |
| **轻量上手** | 无重型 CRM 学习成本，业务员当天可用 |

## 二、信息架构

### 2.1 导航结构

左侧分组导航 + 中心获客入口。菜单按交付阶段标注（①②③），未到阶段的入口不展示：

```
智能获客
├── 智能获客首页      ①（3D 地球占位 + 国家选择 + 关键词搜索「找企业」；「看贸易」入口 ② 开放）
├── 关键人挖掘       ①（联系人/决策人检索）
├── 企业档案库       ①（已落库企业主数据 + 数据维护）
└── 贸易记录        ②（海关数据查询与分析）

沟通触达
├── 邮件营销        ①（发送闭环最小集；自动化多轮 ②；AI 开发信 ③）
├── 我的邮箱        ①（邮箱账号绑定与管理）
└── 送达检测        ②（邮箱有效性、域名信誉）

企业管理（终端企业）
├── 成员管理        ①
└── 数据用量        ①（本企业点数消耗看板）

分销管理（平台/分销商）
├── 组织树与开户     ①
├── 点数账户与划拨   ①
├── 牌价与利润点     ①
└── 交易流水与对账   ①

智能工具
├── AI 分析          ③
├── 智能化 Agent     ③
└── WhatsApp 公开联系人 ③（合规前置）
```

> **【设计决策】** 分销管理与企业管理分两个分组呈现：分销节点管钱和开户（账务域），终端企业管业务和成员（业务域），两者权限模型不同（见 §3.1 U-05），界面入口也必须分离，避免「分销看到下级客户资料」这类越权事故。

### 2.2 核心用户旅程（第一阶段闭环）

```
【搜】智能获客首页 → 选国家 + 输关键词 →「找企业」（企业列表不计费）
   ↓
【落】点开企业 → 详情查询 → 企业档案落库（国家码强校验，判空看 data.id）
   ↓
【挖】关键人挖掘 → 按职位标签筛采购/高管 → 拿邮箱（归属校验 + 可信度分级）
   ↓
【发】邮件营销 → 套模板/多语言 → 群发单显 → 频控保护 → 退订合规 → 退信回写
   ↓
【沉淀】企业数据维护 → 备注 + 补充内容 + WhatsApp 沟通登记 + 聊天截图/附件上传
        → 统一时间线混排呈现
   ↓
【全程成本兜底】计费查询先预估点数 → 确认后执行 → 扣点流水可查
【分销计费链】上级划拨点数 → 牌价强制校验利润点 → 交易流水与利润报表 → 平台对账
```

第二、三阶段分别在此闭环上扩展「贸易记录分析」与「AI/Agent/WhatsApp 触达」，不改变主链路。

## 三、功能需求

阶段定义：**①** = 第一阶段（核心闭环：搜索企业 → 落库 → 发邮件 + 分销计费地基），**②** = 第二阶段（贸易记录与送达检测），**③** = 第三阶段（WhatsApp 与 AI 模块）。

### 3.1 用户管理与多级分销体系 ①

> **需求调整（v2.0）**：系统从「单团队工具」升级为「可多级分销的 SaaS 平台」。组织模型为树状：**平台 → N 级分销（上限 3 级）→ 终端企业 → 成员**。核心设计：**业务数据域与账务数据域分离的双层权限模型**——分销节点管钱和开户，但看不到下级的客户资料。

| 编号 | 需求 | 阶段 | 说明 |
|---|---|---|---|
| U-01 | 账号密码登录 / 登出 | ① | 邮箱 + 密码，密码加密存储；不接 OAuth/LDAP/SSO |
| U-02 | 会话管理 | ① | Token 有效期、超时自动登出 |
| U-03 | 分销层级与组织树 | ① | 树状节点：平台 → 一级分销 → 二级分销 → 终端企业；层级上限 3 级（可配）；节点创建/禁用/搜索；**节点归属一经开户不可迁移**（历史账务不可改），树调整只做新开户 |
| U-04 | 角色权限 | ① | 四角色：平台超管 / 分销管理员 / 终端企业管理员 / 业务员；按「功能菜单 + 数据域」二维授权 |
| U-05 | **双层数据权限** | ① | **业务域**：档案/沟通记录/邮件按终端企业 `tenant_id` 行级隔离，企业内全员可见，**分销节点不可见下级业务数据**；**账务域**：点数账户/划拨流水/消耗统计按分销树向下可见。**必须在数据模型层实现，不能只在前端隐藏** |
| U-06 | 操作审计日志 | ① | 涉及钱必须审计：点数划拨、牌价修改、开户/禁用、敏感操作全部留痕 |
| U-07 | 分销开户管理 | ① | 上级给**直接下级**开户（分销节点或终端企业）；开户即绑定归属、建点数账户、设初始牌价、生成账务档案 |
| U-08 | 成员管理 | ① | 终端管理员邀请/停用本企业成员；分销管理员管理本节点操作员；**不做企业内部门级** |

**验收要点**：U-05 的「分销看不到下级客户资料」既是数据安全红线，也是分销招商卖点；业务域权限校验必须落在 `tenant_id` 行级过滤上。

### 3.2 分销计费与成本中心 ①

> **需求调整（v2.0）**：点数计费是本产品的商业模式本体——平台从腾道按点采购，点数池经多级分销逐级加价二次分销到终端企业，终端按点消耗。计费设计必须保证两件事：**每一级分销商的利润点有机制保障**、**终端用户成本完全透明**。

| 编号 | 需求 | 阶段 | 说明 |
|---|---|---|---|
| B-01 | 点数余额展示 | ① | 平台池余额来自 `/v2/account`（`balance` + `expiresIn`）；分销/终端展示各自账户余额；首页常驻 |
| B-02 | 余额告警 | ① | 各级阈值可配，触发站内 + 邮件通知 |
| B-03 | **查询前消耗预估** | ① | 所有计费查询先预估点数、用户确认后执行（见 D-03），不烧冤枉点数 |
| B-04 | 扣点流水明细 | ① | 对接 `/v2/billing/charges/query`，按月展示扣点时间、接口、扣除点数、计费条数 |
| B-05 | 按节点/成员/模块统计 | ① | 账务域统计：谁消耗了多少点数、花在哪个功能，按分销树向下可见 |
| B-06 | 免费接口标注 | ① | 明确标注哪些操作不扣点（企业列表、联系人社媒、扣点流水等），鼓励用户先用免费探数 |
| B-07 | API 调用配额监控 | ① | 200 次/分钟、30,000 次/日的用量统计与告警。**腾道无配额查询接口，必须自行统计** |
| B-08 | **点数账户体系与划拨** | ① | 三类账户：平台池 / 分销库存 / 终端余额；上级 → **直接下级**划拨；库存校验、余额不为负；划拨单幂等（防重复划拨） |
| B-09 | **定价牌价与利润点校验** | ① | 每级对直接下级设牌价（元/点）；**强制下限校验 `售价 ≥ 进价 × (1+m)`**，最低利润率 m 平台全局可配——**利润点由机制保证而非靠自觉**；牌价变更留痕（接 U-06） |
| B-10 | 分销交易流水与利润报表 | ① | 每笔划拨记录买卖双方、点数、牌价、金额、毛利；按节点/月度汇总进销存与毛利；**可导出对账单**（平台自有账务数据，作为线下结算依据，不受 §4.2 第三方数据导出禁令约束） |
| B-11 | 平台成本对账 | ① | 腾道账单（billing 接口）vs 平台池消耗 vs 对一级销售总额三方对账；平台真实毛利率看板 |

> **收款方式**：线下结算 + 系统对账单，不做线上支付/提现（见 §1.3）。点数流转采用**库存制**（上级先持库存再划拨下级），无坏账。

### 3.3 第三方数据对接与落库

数据源：腾道开放 API V2（`open-api.tendata.cn`）。第一阶段只需要企业、联系人、账户计费三类接口支撑核心闭环；贸易相关接口随第二阶段开放。

| 编号 | 需求 | 阶段 | 说明 |
|---|---|---|---|
| D-01 | 腾道 API 鉴权与令牌管理 | ① | apiKey → accessToken，按 `expiresIn` 提前刷新，全局缓存复用 |
| D-02 | 贸易记录查询与落库 | ② | 对接 `/v2/trade`，支持按 HS 编码、产品描述、国家、时间等条件检索 |
| D-03 | **查询前数据量预估** | ① | 一阶段：对企业详情/联系人等计费查询，按预估结果条数提示点数消耗，用户确认后执行；二阶段扩展：贸易查询调 `/v2/trade/row-count`（**不计费**）先告知「约 N 条，预计消耗 M 点数」 |
| D-04 | 企业详情查询与落库 | ① | 对接 `/v2/company`，生成企业档案——核心链路「落库」环节 |
| D-05 | 联系人查询与落库 | ① | 对接 `/v2/contact`，拿邮箱、职位——关键人挖掘的地基 |
| D-06 | 进出口商汇总名单 | ② | 对接 `/v2/trade/importers`、`/v2/trade/exporters`，按交易规模找头部企业 |
| D-07 | HS 编码分析 | ② | 对接 `/v2/trade/hs-code`，看品类金额占比与均价 |
| D-08 | 联系人社媒地址 | ② | 对接 `/v2/contact/{mailsouId}/social`（**不计费**），随 K-06 一起上 |
| D-09 | 点数余额监控与告警 | ① | 对接 `/v2/account` 查余额，低于阈值告警；区分 `40101`（日请求数用尽）与 `40304`（余额不足）两套文案 |
| D-10 | 数据源覆盖说明 | ② | 向用户展示当前可用数据源清单（腾道共 165 个数据源编码，覆盖 228 个国家地区）；一阶段用静态文案说明即可 |

> **D-03 是我方核心体验要求，不可降级。** 我方按点数实付且点数是逐级购买的商品，若不做前置预估，用户会因为「怕烧点数」而不敢查询，产品直接失去可用性。

**关键约束**（来自腾道文档，必须在产品层体现；贸易相关约束随第二阶段生效）：
- 单次查询时间跨度上限 **3 年**（`catalog=all` 时为 **365 天**）②
- 翻页双上限：`pageNo × pageSize ≤ 10,000` 且 `pageNo ≤ 1,000`，超出需引导用户**拆分查询条件**
- 联系人单次查询上限 **200 条**，达到 200 表示触顶而非实际数量，UI 必须明确提示
- 频率限制 200 次/分钟，数据类接口 30,000 次/日

### 3.4 智能获客首页

对应视觉稿：深色科技风，中心 3D 地球，右侧国家选择器，底部关键词输入。第一阶段「找企业」为唯一核心动作；「看贸易」按钮随第二阶段开放。

| 编号 | 需求 | 阶段 | 说明 |
|---|---|---|---|
| H-01 | 3D 地球可视化 | ①（简化） | 视觉稿核心元素。一阶段用**静态地图或简化地球占位**，不阻塞主链路；Three.js 完整版延后 |
| H-02 | 国家/地区选择器 | ① | 支持搜索、按大洲分组。**必须用 ISO 三位码提交**（腾道要求，传两位码返回 0 条且不报错） |
| H-03 | 关键词搜索 | ① | 产品词 / 公司名。一阶段默认动作 =「找企业」；「看贸易」动作 ② 开放 |
| H-04 | **找企业** | ① | 走企业列表 `/v2/company/list`（不计费）收窄候选 → 企业详情 → 落库。**核心链路入口** |
| H-05 | 看贸易 | ② | 走贸易记录 `/v2/trade`，先预估再拉取；随贸易模块一起开放 |

| C-11 | **企业档案 · WhatsApp 沟通记录入口** | ① | 企业详情页提供「新增沟通记录」入口，供业务员**手动登记**与该企业的 WhatsApp 往来：对方联系人/号码、我方账号、沟通时间、方向（我方发起/对方回复）、文字内容、沟通结果、下次跟进时间。支持新增、编辑、删除 |

| C-14 | 附件分类与管理 | ① | 附件可打分类标签（聊天截图/营业执照/合同/名片/资质/其他，支持自定义）与备注，按分类分组展示；支持**下载回看（用户自上传数据，不受 §4.2 禁令约束）**、重命名、替换、删除；删除为软删除，保留操作人与时间。图片/PDF 在线预览 ② 补全 |
| C-15 | **脱敏、加密与审计** | ① | **对方 WhatsApp 号码属个人数据：列表页脱敏展示（如 `+86 138****8000`）、存储加密，红线**；业务数据权限由 U-05 业务域承担（终端企业行级隔离）；新增、编辑、删除、上传、下载全部写审计日志 |
| C-16 | 待跟进提醒 | ③ | `下次跟进时间` 到期后进入待办/首页提醒；一阶段在时间线展示该字段即可，不做主动提醒 |
| C-17 | **档案补充信息** | ①（新增） | 业务员可对企业档案**手动补充内容**：自定义字段（如主营描述、年采购规模、合作意向）、自由备注。补充内容与腾道原始数据**分区展示并标注「人工补充 + 最后修改人/时间」**，不可覆盖原始数据，保证数据来源可辨 |

> **本条需求的战略价值**：竞品的 WhatsApp 能力（绑定个人号会话存档）依赖**平台授权**，第三方拿不到，所以竞品 CRM 主体里 WhatsApp 沟通其实是断档的——业务员在手机上聊，CRM 里没有记录。我方用「手动登记 + 截图留档 + 补充信息」这条**不依赖平台授权、也无合规风险**的路径，反而能补上这个缺口，形成差异化。
>
> **与 §3.12 WhatsApp 模块的关系**：C-11~C-15 是**记录已发生的沟通**（合规、第一阶段可做）；§3.12 的 W-01~W-04 是**主动挖号码加陌生人**（有封号与 GDPR 风险，第三阶段且合规前置）。两者性质不同，不要混为一谈。
>
> **不在本次范围**：批量导入企业名单（涉及逐行查重、建档、富化触发）是另一个功能，如需另行提需求。

### 3.12 WhatsApp 公开联系人 ③（合规前置）

> ⚠️ **合规定性（必须先决策，不可含糊）**：本模块定位是从**公开数据**中提取 WhatsApp 号码用于主动添加，排第三阶段。这与竞品「打通 WhatsApp 沟通」（在已有会话中沟通）性质不同，风险显著更高：
> - **GDPR / 各地隐私法**：欧盟等地区，未经同意向自然人发送商业信息属违规，处罚力度大。
> - **WhatsApp 平台政策**：批量添加陌生人、未经同意的商业消息，会触发反垃圾机制导致**封号**，且封号不可逆。
> - **腾道数据范围**：腾道联系人社媒接口返回的是 `linkedin` / `facebook` / `twitter` 三类，**不含 WhatsApp 号码**。本模块需另接数据源。
>
> **产品决策建议**：
> 1. 先完成合规评估与数据源确认再开发。
> 2. 落地形态限定为「**号码收集 + 人工逐个添加 + 频次限制**」，**严禁**做批量自动添加/自动群发。
> 3. 产品内必须有显式风险提示与用户确认，并在服务条款中免责。
> 4. 提供地区开关：对 GDPR 严格地区默认关闭主动添加建议。
>
> **与 C-11~C-15 的区分**：企业档案的「WhatsApp 沟通登记」是记录**已发生**的沟通，合规风险低，已在第一阶段；本模块是**主动挖号加陌生人**，两者不互相依赖。

## 四、关键业务规则

### 4.1 腾道 API 硬性约束

以下规则来自腾道 API 的硬性约束，**必须在产品层显式处理**，否则会出现「不报错但结果错误」的静默失败。贸易相关规则（区间参数、`conditionGroups`、数据源分隔符等）随第二阶段生效，但防腐层（统一响应解析、翻页守卫、DTO 分离）第一阶段就必须建好。

| 规则 | 说明 | 产品处理方式 |
|---|---|---|
| **国家码必须三位** | 传两位码（如 `CN`）返回 0 条且**不报错** | 前端强制三位码，国家选择器直接输出 Alpha-3 |
| **多值分隔符不统一** | `country`（数据源）用**逗号**；`hsCode`、国家码等业务字段用**分号**；联系人 `positionTag` 用**逗号**。业务字段用错分隔符返回 0 条且**不报错** | 由后端统一拼装，前端不暴露分隔符概念 |
| **区间参数两端必填** | `["1000",""]` 返回 0 条；`["1000"]` 服务端错误 | 前端区间控件强制双值；单边筛选自动补极大/极小值 |
| **请求与响应字段大小写不一致** | 请求 `sumOfUSD`，响应 `sumOfUsd` | 后端 DTO 分离，禁止字段名回填 |
| **页码越界静默归零** | `pageNo > 1000` 时返回 0 条、`total` 归零、`code` 仍为 `"200"`，与「真的没数据」无法区分 | **请求前校验**，越界时提示拆分条件，绝不依赖响应判断 |
| **企业判空只看 `data.id`** | 未匹配时结构完整，`contactMethods` 空数组、`tradeStats` 全 0 | 后端统一判空逻辑 |
| **联系人 `total`=200 是上限** | 非实际数量，超出后翻页返回空列表且 `code` 为 `"200"` | UI 明确提示触顶 |
| **联系人归属可能不符** | 返回的 `companyName` 与查询名不同是常态 | 逐条标注归属 + 提供「仅完全匹配」过滤 |
| **`tradeStats` 常返回全 0** | 口径固定近一年，不接受时间参数 | 全 0 时不呈现为「无贸易」，改用汇总接口取指定区间 |
| **业务成败看 `success` 不看 HTTP** | 参数错误、令牌失效、余额不足均返回 HTTP 200 | 后端统一响应解析层 |
| **`40101` 与 `40304` 分别处理** | 每日请求数用尽 vs 余额不足，是两套独立判断 | 不同文案与不同恢复路径（次日恢复 vs 需充值） |

### 4.2 数据导出禁令（全局规则，已决策）

**第三方数据（腾道来源的企业、联系人、贸易记录）全端不提供任何导出/下载能力**：

- 产品内不出现「导出 Excel / 导出 CSV / 下载名单」等入口（T-10 已从功能清单移除）；
- 后端不提供批量拉取接口；列表查询分页上限收紧，防止以翻页方式变相批量抓取；
- 对异常高频、大批量访问做监控告警（防爬防泄，见 §五）。

**明确例外**（不属于第三方数据，不受此禁令约束）：

- 用户**自上传**的聊天截图与附件（C-12/C-14）可下载回看；
- **内部账务对账单**（B-10）可导出，作为线下结算依据。

| 类别 | 要求 |
|---|---|

| **并发与限流** | 全局令牌桶控制 ≤ 200 次/分钟；日请求数计数器 ≤ 30,000，接近上限自动降速并告警 |
| **可用性** | 核心链路可用性 ≥ 99.5%；腾道接口异常时降级为本地缓存数据并明确标注数据时效 |
| **数据一致性** | 落库去重以腾道记录 ID / `mailsouId` 为业务主键；批量任务支持断点续跑 |
| **账务一致性** | 点数账户余额**不允许为负**；划拨单幂等（防重复划拨）；交易流水只增不改（红冲调账）；牌价强制下限校验在服务端执行 |
| **多租户隔离** | 业务域按终端企业 `tenant_id` 行级隔离，分销节点不可见下级业务数据；账务域按分销树向下可见；全部在数据模型层实现 |
| **防泄露** | 第三方数据无导出入口（§4.2）；异常高频/大批量访问监控告警；敏感操作（划拨、牌价修改、开户、批量删除）全量审计 |
| **安全** | apiKey、accessToken、邮箱授权码、WhatsApp 号码经密钥管理服务/加密存储，**严禁硬编码或进代码仓库**；日志不落完整凭据 |
| **合规** | GDPR 等地区的数据处理与退订机制；邮件营销强制 List-Unsubscribe；WhatsApp 主动挖掘模块（③）合规前置评估 |
| **可观测** | 每次外部调用记录 `traceId`、接口路径、耗时、HTTP 状态、脱敏参数；腾道排障强依赖 `traceId` |
| **成本** | 计费查询 100% 走预估确认；免费接口优先；重复请求幂等保护，避免重复扣点 |
