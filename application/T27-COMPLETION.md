# T27 系数变更通知、生效与全链额度覆盖核验

## 实现

- 平台管理员发布未来生效的 X 通知，保存原 X、新 X、通知内容和时间；同一待生效通知唯一，请求标识重试幂等。平台界面可在告知时间到达后执行生效；各组织工作台显示系统内通知。
- 生效事务先锁计价、全部报价或在途查询，再锁平台、分销及终端余额。全链余额按平台库存、各分销库存、各终端余额各计一次；冻结和销售预留已包含在余额中，不另加。三类在途查询按锁定旧 X 计需覆盖点数；明确记录的上游已扣、本地未结算点数从该在途暴露中剔除，并单列证据。其余余额按拟生效 X 换算，需求向上取四位。降低 X 时读取实时腾道余额，缺口拒绝生效。
- 旧待结算授权保留旧 X；仅报价未执行的旧 X 查询在生效时标记过期，执行会拒绝并要求重新报价。已有余额、历史销售和历史成本不重算。补缺口继续使用既有 `coverage` 采购路径，只增上游充值账、不增销售库存。生效覆盖快照和上游账户 traceId 留存。

## 已验证

- 独立、每次随机命名的 `t27_*_test` PostgreSQL 数据库，55436 端口；HTTP 3177，Chromium 3178，浏览器输出 `test-results-t27`。测试自动删除自己的数据库。
- `npx tsc -p tsconfig.server.json; node --test dist/tests/coefficient.test.js` 通过。覆盖通知幂等/冲突、提前生效拒绝、上游仅 8 点时拒绝、补缺口采购生成内部点数 0、上游余额到 18 点后并发生效一次、旧授权 X=1.0000、新报价 X=0.5000、旧报价拒绝、历史余额不重算、新销售用途采购按新 X 入账。夹具让列表 `source_id=list-id-B`、内部候选 UUID、报价 UUID、查询 UUID 各不相同；重报价仍使用原候选 UUID。
- 核算夹具含平台库存 4 点（预留 1）、分销库存 3 点（预留 1）、终端余额 3 点（冻结 3），以及详情、联系人、产品名单各一笔在途。详情旧 X=1 的 2 点冻结中有 0.5 上游点已扣、本地未结算；全链需覆盖 16.5000 上游点，三笔冻结共 3 点只计一次。
- `npm run build` 通过；`node node_modules/@playwright/test/cli.js test --config playwright.t27.config.ts` 通过。浏览器平台发布通知、到时生效、显示新 X，终端登录看到系统内通知。

## 未验证及边界

- 未接正式腾道账号、真实充值凭证或正式账单；测试的实时账户响应是受控夹具。跨系统并发扣费无法由本地 PostgreSQL 锁保护，正式上线前需结合真实账户实时余额、账单延迟和并发查询复核覆盖策略。
- 未重跑共享工作区全部 T06–T13/T22 浏览器套件，也未验证生产多实例压力、长期未决查询或所有跨票订单流程。T27 独立测试覆盖相关冻结、预留和采购核算数据链；T22 邮件链路由另一会话负责。本票未修改销售历史或实现 T28 报表。
